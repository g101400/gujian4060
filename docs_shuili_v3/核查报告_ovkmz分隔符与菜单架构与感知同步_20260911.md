## 一、ovkmz（奥维）导出 —— 分隔符核查

### 1.1 结论（当前 v3.68 代码）

| 场景 | 文件位置 | 分隔符 | 单条格式 |
|---|---|---|---|
| 导出 ovkmz（奥维） | KML `<description>`（备注正文） | **`|` + 换行**（JS 字面量 `"|\n"`） | `键 : 值`（冒号左右各一个空格） |
| 导出 ovkmz（奥维） | `<ExtendedData>`（结构化，供无损回读） | 每个属性一条 `<Data>` | `<Data name="键"><value>值</value></Data>` |
| 导出建筑物表格 CSV | 第 8 列（表头 `comment`） | **`|`** | `键:值`（冒号两侧无空格） |

代码位置（shuili-v329/assets/app.js）：
- `L11774`：`desc = attrs.map(a => a[0] + " : " + a[1]).join("|\n")`
- `L11744-11747`：`ExtendedData`（管理单位 / 管理站 / 渠道 / 建筑物类型 + 全部自定义属性）
- `L12521`：`params` 列 `attrs.map(a => a[0]+":"+a[1]).join("|")`

### 1.2 用户看到的 `;` 版本从哪来

用户提供的样本 `备注:; 桩号（Km+m）:1+508; 设计流量（m3/s）:70; …` 使用的是 **`; `（分号+空格）**，这是 **v3.67 及更早** 的导出格式：

| 版本 | ovkmz `description` | CSV `comment` 列 |
|---|---|---|
| ≤ v3.67（旧） | `键 : 值` 用 **`|`** 连接（**不带换行**） | `键:值` 用 **`"; "`** 连接 |
| ≥ v3.68（当前） | `键 : 值` 用 **`|\n"`** 连接（`|` + 换行） | `键:值` 用 **`|`** 连接 |

> 即：用户手里的文件是 v3.68 之前导出的。用 v3.68+ 重新导出，八个参数间即由 `; ` 变为 `|`；ovkmz 内则为 `|`+换行。

### 1.3 导入侧兼容性（已具备，无需改动）

- `detectCSVDelim`：仅扫首行，候选 `, ; TAB`，**排除 `|`**（`|` 是参数内部连接符，不参与列切分）。
- `parseAttrBlob`：参数串同时支持 `|` / `;` / 换行 三种分隔 + `键:值` / `键：值`。
- `parseDescAttrs`（回读 ovkmz）：**优先按 `|`**，其次按换行。

=> 新旧两种导出文件均可被当前版本正确导入，往返兼容。

### 2.2 现存混乱点（5 处）

1. **「导入/导出」被拆散在两处**：`②数据管理`（批量导入建筑物/照片、导出表格/照片）与 `③传输与共享`（导入导出 ovkmz/ovobj/obj）本质是同一类动作，用户找"导入"要翻两个组。
2. **「传输与共享」语义超载**：10 项里混了三种东西 —— ①格式互转（ovkmz/ovobj/obj）②设备间传输（手机互传、统信/安卓照片搬运）③传输参数（WiFi/网盘/续传）。
3. **「设置」严重超载（16 项）**：把「功能」当「设置」放 —— 尤其 **`知识库管理` 是功能**，不是配置项；还有「管理所统一确认」「组织与类型管理」实为数据治理工具。
4. **两个 AI 组概念重叠**：`⑤智能AI`（问答/更新/纠错）与 `⑥智能化内核`（模糊检索/反查/报告/PDF转Word）用户难分辨谁是谁。
5. **备忘录不属于运维**：`④运行维护` 里塞了「写备忘录 / 我的备忘录」，属个人记事，与运维计划/巡视不同类。

### 3.2 根因

- `sync_all_mirrors.py` 的 `CORE` 校验只做 **同一产品 canonical → 其自身镜像** 的一致性，**从不做跨产品（水利 ↔ 感知 ↔ 古建）公共模块比对**。
- 历史上「知识库整句切片（v3.55 / 1.31）」是**以水利为样板**升级的，`kb_rag.js` / `ai_module.js` / `ovobj_bridge.js` 三个文件升级后**未回灌**到 perc/gujian。

### 3.3 建议（本次不执行）

1. 在 `sync_all_mirrors.py` 增加**跨产品公共模块一致性门禁**：对 `kb_rag.js`、`kb_vector.js`、`kb_core.js`、`photo_gesture.js`、`ctx_menu.js`、`secure_boot.js`、`ai_module.js`（除产品字段）、`ovobj_bridge.js` 做三端 md5 比对，不一致即 FAIL。
2. 把水利的 `kb_rag.js`、`ai_module.js`（通用逻辑部分）、`ovobj_bridge.js` **回灌**至 perc/gujian，回归验证后随下一版发出。
3. 修正感知/古建 version.json 与四端对照单中被误标 ✅ 的两项。

### 5.2 「非 WiFi 网络」弹窗 —— 误报与智能调整

**弹窗实现**：`app.js` `L1452 ensureWifi(action, cb)`：

```js
if (net !== "wifi") {
  ask("非 WiFi 网络",
      "当前不是 WiFi（移动网络/无网络），" + action + "可能消耗大量流量且耗时较长，是否继续？", ...);
}
```

**全部 6 个调用点分类**：

| 行号 | 触发动作 | 是否走网络 | 是否该弹「非WiFi」 |
|---|---|---|---|
| L1990 | 手机互传 · 从服务端下载（>3GB） | ✅ 走 WiFi 局域网 | **保留**（真网络） |
| L10121 | 导出全部照片（写盘打包） | ❌ 纯本地 | **误报 → 应移除** |
| L10665 | 导入 ovkmz（读本地文件） | ❌ 纯本地 | **误报 → 应移除** |
| L11580 | 导出 ovkmz（写本地文件） | ❌ 纯本地 | **误报 → 应移除** |
| L12181 | 导出照片（zip/7z 打包） | ❌ 纯本地 | **误报 → 应移除** |
| 网盘上传/下载、升级包下载 | （未用 ensureWifi） | ✅ 走公网 | 建议另行纳入统一「联网提示」 |

**结论**：4 个本地导入/导出场景全部被误判为「可能要耗流量」，弹的是无意义警告。

**智能调整方案（待开干，采纳用户要求）**：
1. 本地导入/导出**不再走 `ensureWifi`**，改为新的 `confirmLocal(action, bytes, cb)`：
   - `bytes < 阈值`（建议 100 MB）→ **不弹任何窗口**，直接执行；
   - `bytes ≥ 阈值` → 弹 **标题「操作提示」**，内容 **「本次操作文件约 XX MB，耗时较长，是否继续？」**（按钮：继续 / 取消）。
2. 大小来源（已确认可用）：
   - 导入 ovkmz：`window.Android.fileSize(path)`（桥已存在，见 `app.js:1318/1326`）；
   - 导出 ovkmz / 导出照片 / 导出全部照片：照片字节合计（`fileSize(绝对路径)`，base64 场景用 `data.length`）。
3. 真网络操作（手机互传下载、网盘上传/下载、升级包下载）**保留**「非 WiFi 网络」警告；对其中确实很小的传输可同样按大小短路。

### 6.1 问题一：筛选菜单「管理处」与 设置→组织与类型管理「管理处」不对应

**现象核对：成立。**

| 入口 | 选项来源（代码） | 实际选项 |
|---|---|---|
| 筛选菜单 → 「管理处」chip | `guanchuOptions()`（`app.js` L565-581）= `getCustomGuanchu()` + **硬编码 `CANONICAL_GUANCHU`（常量 5 个处）** + 建筑数据里出现过的 `b.guanchu` | **5 项**：京密引水 / 潮白河 / 海河 / 永定河 / 北运河管理处 |
| 设置 → 组织与类型管理 → ①层级名称 → 「管理处」 | `orgStore().guanchu`（`app.js` L597-621），默认 `[ORG_DEFAULT_NAMES.guanchu]` | **仅 1 项**：京密引水管理处 |

**根因（一行之差）**：`orgStore()` 对 **所（suo）** 做了权威清单兜底合并 ——

```js
if (lv.k === "suo") CANONICAL_OFFICES.forEach(o => { if (saved.suo.indexOf(o) < 0) saved.suo.push(o); }); // L615
```

**但对 管理处（guanchu）没有做同样的 `CANONICAL_GUANCHU` 合并** → 另外 4 个处从未进入 `org_levels.guanchu` → 该面板不列出它们 → 自然「除了京密引水管理处，其他 4 个处不能删除或修改名称」。这与用户观察完全一致。

**连带的 4 个副作用（均实测）**：

1. **删了也复活**：即使把「京密引水管理处」在管理面板删掉，筛选栏仍会显示它 —— 因为 `guanchuOptions()` 无条件追加常量 `CANONICAL_GUANCHU`。→ 管理面板的「删除/改名」**对筛选栏不生效**，改动无法闭环。
2. **下拉同缺**：「组织与类型管理 → ②默认设置 → 默认管理处」下拉（L4021-4035，走 `levelOptions("guanchu")` = `orgStore().guanchu`）同样只有 1 项。

4. **建筑物编辑表单根本没有「局 / 管理处」字段**：`openEdit` 表单（L5494-5526）字段为 名称 / 管理所 / 管理站 / 段 / 建筑物类型 / 经纬度 / 参数 / 照片 —— **无 局、无 管理处**。

**另发现一处语义冲突（CSV / 属性导入）**：`FIELD_ALIAS.office` 把 **「管理处」「所属管理处」当作 office（管理所）的别名**（L11044）：

## 七、需求分析与最优化方案：感知应用智能集成水利一张图（只读分析 · 待开干）

> ⚠️ **本节（§7）已因需求变更作废**，以 **§8 修正版**为准：不再"把水利一张图功能整体集成进感知"，改为"水利 App 保持独立；感知 App 仅集成**水工建筑物底图层**"。

> 需求 5 条（用户原文）：①感知设备一张图把水利一张图功能智能集成进来（感知设备皆为水工建筑物服务）②智能问答/查询支持跨实体周边关系（某建筑物周边有几个感知设备 / 反之）③两类目标共存的最优化方案 ④筛选/查询/导入/导出/导出列都要有"水工建筑物 or 感知设备"明确可选项 ⑤逻辑上水工建筑物是基础、感知设备为其服务。

### 7.1 现状事实（代码实证）

**A. 两 App 同源同构，差异极小**

- `index.html` 脚本清单完全一致（14 个，含 `data.js / kb_building_seed.js / ovobj_bridge.js / ai_module.js / kb_core.js / kb_vector.js / photo_gesture.js / ctx_menu.js / app.js`）。
- `app.js`：水利 509,737 B vs 感知 507,249 B。真正的差异只有：`LS_KEY`（`shuili_map_v2` vs `perc_map_v2`）、数据数组名（`SHUILI_DATA` vs `PERCEPTION_DATA`，L2104/2114/2134）、AI `domain`（`shuili` vs `perc`）与 `appName`、备忘录文案等产品常量。
- → **合并成"单应用双实体"的改造成本远低于两个应用互抄**：同一套 UI / 筛选 / 导出 / 菜单代码可直接复用。

**B. 数据模型：字段名相同、语义不同（最大坑）**

| 维度 | 水利（SHUILI_DATA 557 条） | 感知（PERCEPTION_DATA 1125 条） |
|---|---|---|
| 字段 | id,name,office,station,chan,btype,path,attrs,photos,geom,lon,lat | id,name,office,station,chan,btype,geom,lat,lon,attrs,photos,noCoord,subsystem |
| btype | **21 类水工建筑物**（交通桥 112、雨水口 69、道路 67、分水闸 60、穿渠项目 35、过渠涵洞 28、节制闸 17…） | **4 类设备子系统**（视频监控 889、地下水源监测 169、大坝安全监测 41、雨水情监测 26） |
| chan 语义 | **段 / 渠道**（温泉所、龙山管理所、史山所…） | **信号类型**（数字 292、力学量传感器 170、模拟 56、电学量传感器 42、湿度水分 21…） |

**C. 可复用的既有能力（好消息）**

- **向量内核已多域化**：`kb_vector.js` 顶部即有 `shuili / perc / gujian` 三套 CFG（label 分别为"建筑物 / 感知设备 / 景点"），只是 `items()` 取"第一个命中数组"，仍是单库假设。

- **持久化单 key**：`load()/save()` 用唯一的 `LS_KEY`（水利 L2106 附近）→ 双数据集**必须分库分 key**，否则保存设备会覆盖建筑物。

### 7.2 需求 3 —— 最优化方案（推荐 + 备选）

**★ 推荐：单应用 · 双实体内核（Kind-Aware Unified Kernel）**

1. **数据层**：两个独立数组 + 两个独立持久化 key，统一"当前工作集"视图。
   - `DS.get("building" | "device")` / `DS.set(...)` / `DS.all()`；`kind` 写入每条实体。
   - 建筑沿用 `shuili_map_v2`，设备沿用 `perc_map_v2`（老用户数据零迁移）。
2. **模型层**：不做字段强行合并，改为「共享字段 + 类型专属字段 + 映射层」。
   - 共享：id / name / office / station / attrs / photos / geom / lat / lon
   - 建筑专属：`path`、段（现 `chan`）、21 类 btype
   - 设备专属：`subsystem`、`noCoord`、信号类型（现 `chan`）、4 类 btype
   - 读写经 `SCHEMA[kind]` 映射，界面统一叫法（建筑"段/渠道"、设备"信号类型"），**导入导出带上 kind 标识**，老文件默认按 building 解析。
3. **关联层（核心）**：`Link` 主从关联表（localStorage `link_table_v1`），`building → devices[]`。
   - 自动关联三源：①空间距离 ≤ R（默认 200 m，可调）②同管理所/站 ③名称包含（如设备"向阳闸管理对东"含建筑"向阳闸"）。
   - 手动关联：设备详情内"绑定服务对象 / 解除绑定"。
   - 全量反向计算成本：1682 实体两两距离 ≈ 62.6 万次，毫秒级，无需预建索引（可缓存）。
4. **交互层**：全局 **目标类型开关**（🔷水工建筑物 / 🟢感知设备 / ⬜全部），持久化进 SETTINGS，贯穿筛选、查询、周边、导入、导出、导出列、统计、AI。
5. **AI 层**：`listAll()` 增加 kind 维度；"周边/关联/统计"类问题走**本地结构化计算 → 再交 LLM 组织语言**（保证数字准确、不臆造）。
6. **发布层**：合并后一次构建四端。体积估算：app.js ~510 KB + data 338 KB + 344 KB + kb_seed 306 KB + 298 KB ≈ **1.8 MB JS**，离线 WebView 可接受（可选 gzip / 懒加载种子）。

**备选 A（改动最小）**：感知应用只把水利数据集作为**"服务对象"只读图层**并入（建筑不可编辑，仅供定位/关联/统计）。优点：几乎不动感知现有交互；缺点：需求 4 的"导出建筑物/编辑建筑物"受限。

**备选 B（反向）**：以水利为主程序并入设备 —— 与需求 1 字面（并入**感知**应用）冲突，不推荐。

**备选 C**：两个独立 App + 共享关联模块 —— 不满足需求 4 的"统一可选"，不推荐。

### 7.3 需求 4 —— 四个入口的"类型可选"设计

- **筛选**：面板顶部加三段开关「水工建筑物 / 感知设备 / 全部」；切换后 chip 组整组替换 ——
  建筑组：管理处（§6 修复后 5 项）/ 管理所 / 管理站 / 21 类建筑类型；
  设备组：4 类子系统 / 管理所 / 管理站 / 信号类型。
  切换即重算计数与默认筛选（分别持久化）。
- **查询**：搜索框旁 scope 徽标（🔷/🟢/⬜）+ 一键切换；关键词与 scope 联合过滤；历史关键词按 scope 分组。
- **导入**：文件识别后自动归库 —— 命中建筑特征（btype ∈ 21 类 / 有 path / 无 subsystem）→ 建筑库；命中设备特征（有 subsystem / noCoord / 设备类型）→ 设备库；无法判定则弹「导入为：建筑物 / 感知设备」二选一；导入预览显示"识别结果 + 条数 + 目标库"。
- **导出**：导出前弹 scope（建筑物 / 感知设备 / 全部）；文件名与文件夹组成字段随 scope 切换；ovkmz / ovobj / CSV / ZIP 各自适配；选"全部"时输出两个文件（或单文件加 kind 列）。
- **导出列**：列配置**按 scope 分别记忆** ——
  建筑：名称 / 管理处 / 管理所 / 管理站 / 段 / 建筑物类型 / 纬度 / 经度 / 参数说明 / 巡视次数；
  设备：名称 / 子系统 / 管理所 / 管理站 / 信号类型 / 纬度 / 经度 / 参数说明 / 有无坐标。

### 7.4 需求 2 —— 跨实体自然语言"周边/关联"查询

新增本地「周边与关联查询」引擎（先算后说，复用 `distanceTo`）：

- **意图解析**：（实体 A：名称或类型）+（周边/附近/多少米内）+（实体 B：类型/数量）。支持正反两向：某建筑物周边有几个感知设备 ↔ 某感知设备周边有几座水工建筑物。
- **计算**：以 A 坐标为中心、半径 R（默认 200 m，"XX米内"可覆盖）筛 B；A 无坐标（设备 236 条 `noCoord`）时给出"按管理所/站"替代口径并说明原因。
- **回答样式**：先结论（"共 3 个感知设备，最近 45 m"）→ 再清单（名称 / 类型 / 距离 / 所属所站）→ 支持一键定位、导出 CSV/Word。
- **交互入口**：①地图点选任意实体 → 气泡"周边设备(N)"；②AI 面板自然语言；③向量反查（kb_vector）共用同一引擎。

### 7.5 需求 5 —— 主从逻辑（建筑物为基础，设备为服务）

- **数据**：building 为主、device 为从；device 增加可选 `servTarget`（服务对象 = 建筑 id 或名称）。
- **界面**：查看建筑物 → 显示「服务设备」区（数量徽标 + 列表 + 一键定位）；查看设备 → 显示「服务对象」区（所属建筑物）。
- **统计**：按建筑物统计"挂载设备数 / 设备类型构成"；按设备统计"服务覆盖建筑物数"；可一键导出报表（doc/docx/pdf，复用 kb_vector 报告能力）。
- **校验与防误删**：删除建筑物时提示"其关联的 N 个设备将变为未绑定"；删除设备不影响建筑物；建筑为**基础数据**，删除仍走二次确认（沿用现有批量删除确认机制）。

### 7.6 风险与代价（必须提前认领）

4. **无坐标数据**：感知 236 条 `noCoord` → 周边查询、地图渲染、距离计算需统一过滤并给替代口径。

## 八、修正版需求分析（替代 §7）：感知 App 仅集成"水工建筑物底图层"（只读分析 · 待开干）

> 需求变更说明：用户考虑到实施风险，**撤回** §7 的"把水利一张图功能整体集成进感知设备 App"方案，改为更克制的做法 —— 水利 App 与感知 App **各自独立**，感知 App 只把"水工建筑物"作为**一个基础数据层/文件**引入（可查询、可搜索），并保留感知原有全部功能不变。

### 8.1 修正后需求（5 条）

1. **水利一张图保持相对独立**，不混入感知设备 App。
2. 感知 App **只集成"水工建筑物"作为基础底图数据层**（单独数据层/文件，可查询、可搜索），**不再集成水利一张图的其它功能**。
3. 感知 App 内**建筑物与感知设备数据独立分开**；只能通过**单独导入**（水利导出的 ovkmz / kmz / csv 等）写入建筑物数据，**导入只影响建筑物数据，不得影响或覆盖感知设备数据**。
4. 智能问答/查询支持跨层自然语言：**某建筑物周边有几个感知设备** ↔ **某感知设备周边有几座水工建筑物**。
5. 筛选 / 查询 / 导航均增加明确可选项（**默认 = 感知设备**）；**原有感知导入导出功能保持不变**；**新增子菜单「导入水工建筑物」**；点击建筑物可查看 / 修改建筑物信息（含图片），并可**新增建筑物或地点**。

> 注：需求 5 里的"导航"在本 App 对应「地图和位置」组的定位我的位置 / 获取坐标 / 周边搜索 / 列表视图 / 底图切换（现菜单无独立"导航"项），scope 开关应覆盖该组。

### 8.2 现状支撑（代码实证，与 §7.1 同源）

- 感知菜单现有 8 组：置顶（查询/筛选）、地图和位置（定位/获取坐标/底图切换/测距/周边搜索/列表视图/添加建筑物）、数据管理（批量导入建筑物/批量导入照片/导出建筑物表格/导出照片/清理导入缓存/删除添加的照片）、传输与共享（导入ovkmz/导出ovkmz/导入ovobj/导出ovobj/导入obj/导出obj/传输设置/手机互传/导出照片到统信/从安卓平台导出照片）、运行维护、设置、信息与帮助。
- 数据是**单库单 key**：`LS_KEY = "perc_map_v2"`（L160），`load()/save()` 只读写这一份（L2104-2134），数据源 `window.PERCEPTION_DATA`。`BUILDINGS` 是全局唯一数组，`app.js` 中共 **117 处引用**。
- **写操作只有 6 处**：载入/复位 3 处（L2110、L2114、L2134）、新增 push（L5720）、删除 filter（L5744、L7014）、导入 push（L8731、L10827、L11512）。→ **改动面集中在写操作**，读取处可整体沿用。
- 已有"作用域钩子"：`Object.defineProperty(window,"BUILDINGS",{get:...})`（L3339）→ 可平滑改成"按 scope 返回数组"。
- 空间能力已有：周边搜索用 Leaflet `distanceTo`（L6380）。
- id 命名天然分域：设备 `p1…p1125`，水利建筑 `b1…b557`（实测），跨库不易碰撞。

### 8.3 技术方案（推荐）

**核心手法：把"全局单数组"升级为"作用域视图"，默认作用域=感知设备。**
这样一来，现有 117 处引用中**除 6 处写操作外全部零改动**地跟随 scope 工作；且**默认 scope=设备 → 感知原有筛选/查询/导入/导出行为完全不变**，正好满足需求 5 的"保持不变"。

- **A. 数据层（双库双 key）**
  - `DEVICES`：感知设备，`PERCEPTION_DATA` + LS `perc_map_v2`（**沿用，全部逻辑不动**）。
  - `WBUILDS`：水工建筑物，新 LS key（建议 `perc_water_v2`），数据源可为空（默认）或随附 `water_data.js`（可选，内置一份建筑底图）。
  - `SCOPE ∈ {device(默认), water, all}`，持久化进 SETTINGS；`window.BUILDINGS` 的 getter 返回当前 scope 的数组（`all` 返回**只读合并视图**）。
  - 写操作按 kind 路由：`storeOf(kind).push/splice` + `saveOf(kind)` 落各自 key；**导入建筑物只写 `WBUILDS`**（需求 3 的硬约束）。
  - id 命名空间：设备 `p*`、水利建筑 `b*`（导入保留原 id）；App 内新建用 `w*` 前缀，防止与设备/原建筑碰撞。

- **B. 集成入口（需求 5）**
  - **新增子菜单：数据管理 →「导入水工建筑物」**（支持 ovkmz / kmz / csv / ovobj / obj），复用现有 `importKmz` 解析器，但**目标库固定为 `WBUILDS`**；导入确认框写明「仅更新建筑物数据层，不影响感知设备数据」+ 显示识别条数 + 追加/覆盖 二选一。
  - 建议同时给一个对称的「导出水工建筑物」（便于回传水利 App 或备份）；若不需要，则至少提供「清空建筑物层」。
  - **不集成**水利 App 的其它能力（巡视/运维计划/预案/报告生成/PDF→Word/知识库管理菜单等）。

- **C. 筛选 / 查询 / 导航 的 scope 可选项（需求 5）**
  - 筛选：面板顶部三段开关「🔷水工建筑物 / 🟢感知设备（默认）/ ⬜全部」；chip 组随 scope 整组替换（建筑：管理处 / 管理所 / 管理站 / 21 类建筑类型；设备：4 类子系统 / 管理所 / 管理站）；各 scope 的默认筛选**分别持久化**。
  - 查询：搜索框旁 scope 徽标 + 一键切换，关键词随 scope 过滤；历史关键词按 scope 分组。
  - 导航（地图和位置组）：定位我的位置 / 获取坐标 / 周边搜索 / 列表视图 全部加 scope 选择；**周边搜索的"中心"与"目标"都可选建筑/设备**（这条同时满足需求 4）。
  - 地图分层（建议）：建筑物层作为**基础底图风格**（灰/绿方块或线）置于下层，设备层保持现有彩色图标置上层；按 scope 显隐 + 图例分组（`buildLegend` 扩展）。

- **D. 跨层周边问答（需求 4）**
  - 复用 `distanceTo`；解析「A 周边 B 的数量/清单」，A、B 各自可为建筑或设备（正反双向）。
  - 半径默认 200 m，"XX 米内"可覆盖；A 无坐标时（设备 236 条 `noCoord=true`）改给"按管理所/站"替代口径并说明原因。
  - 回答样式：先结论（"共 3 个感知设备，最近 45 m"）→ 再清单（名称 / 类型 / 距离 / 所属所站）→ 一键定位 + 可导出。
  - **周边类问题一律本地结构化计算完成后再交 LLM 组织语言**，杜绝数字臆造。

- **E. 建筑物查看 / 编辑 / 新增（需求 5）**
  - 点击建筑物（地图 marker 或列表）→ 详情/编辑：名称 / 管理处 / 管理所 / 管理站 / 段 / 建筑物类型 / 经纬度 / 参数 / 照片；沿用现有编辑表单与 `photo_gesture.js` 图片预览（电脑拖拽缩放、手机捏合/长按菜单）。
  - 支持「新增建筑物（点地图定位）」，并支持「新增地点」（无类型/无参数的轻量点位）。
  - 所有编辑**只作用于 `WBUILDS`**，由 scope 路由保证**永不触碰设备库**。

### 8.4 实施风险（修正版，显著低于 §7）

1. **作用域视图改造是唯一高风险点**：117 处引用里 6 处写操作必须逐一改为 kind 路由，漏改会导致"编辑建筑物时误改设备库 / 存错 key"。→ 对策：写操作强制显式传 kind + 加运行时断言 + 写回归脚本（导入建筑物后校验设备库 md5 不变）。
2. **LS 配额**：设备库 ~344 KB + 建筑库 ~338 KB ≈ 700 KB JSON；`save()` 已有"存储已满"提示可复用。
3. **渲染量**：默认只渲染设备层；切"全部"时 1682 点，需懒渲染/分层裁剪，避免卡顿。
4. **字段同名异义**（`chan`/`btype`/`office`/`station`）：建筑层显示走 `SCHEMA.water` 映射（建筑叫"段/渠道"，设备叫"信号类型"）；导入文件带 kind 标识，老文件按"当前导入入口"判定。
5. **知识库 / AI 需按 kind 分库**：`kb_vector.js` 的 `items()` 是单库假设、`KBV_APP` 两端都没设置（感知端标签错显示"建筑物"）；`ai_module` 的 `listAll()` 需支持 scope，否则"全部"模式下问答会串库。
6. **与水利 App 解耦**：建筑物数据**只经导入进入**，不做双向同步（避免回写污染水利 App）；需回传时用「导出水工建筑物」手动带回。
7. **发布范围**：只动感知 App（独立发版，如 v1.46+）；**水利 App 不动**（不 bump、不重出），避免牵连回归面。
