## 问题 1：添加建筑物弹窗「选照片后已填字段的对勾标记丢失」

**现象**：新增/修改建筑物时，先填名称、管理所、管理站等参数（显示对勾 ✓），再点「选择文件」上传照片，顶部已填字段的对勾消失（字段值仍在）。

**根因（已坐实）**：`openEdit(b)` 每次选照片都会整体重建弹窗 DOM（`editBody.innerHTML = ...`），位于
- 水利：`android-build/shuili-v329/assets/app.js` 第 1394-1407 行（`$("fPhotos").onchange` 内 `openEdit(b)`）
- 感知：`android-build/perc-v13/assets/app.js` 同源
- 古建：`travel/webroot/app.js` 同源

重建后字段值通过 `b.name` 等回填（值不丢），但**对勾标记依赖的运行期状态被清空**（无论 CSS `:valid` 之外的 JS class，还是其它派生态），且重建后 `oninput` 不再触发 → 标记不重绘。

**影响范围**：水利 / 感知 / 古建 三端 Web+原生壳（安卓/Win/UOS）一致，因同源 `openEdit`。

**修复方向（待确认方案）**：
- A. 选照片时**不再整段重建弹窗**，改为仅 `append` 新照片卡片到 `#phGrid`（增量更新，保留其它 input 焦点与校验态）；
- B. 若必须重建，重建后统一跑一次 `refreshValidity()` 重涂校验标记；
- C. 把「对勾」改为纯派生（input 有值即显示），与重建无关。

## 问题 2：批量导入照片 ZIP「匹配到 N 张，点确定保存却为 0 张」

**测试样本**：`C:\Users\admin\Downloads\埝头管理所建筑物照片.zip`（13MB，39 张图，结构 `埝头管理所建筑物照片/<类别>/<建筑物名>.jpeg`）。
用户反馈：16 张匹配点确定，保存照片应是 16，实际为 0。「修复多次没弄好」。

**数据流（已追踪）**：
1. 原生端 `onPickFiles` -> `Android.unzipImages` 解压 -> `onUnzipImages(json)` 回传 `{name,path,folder}`（path = `inbox/uz_xxx/<照片名>` 绝对路径）
2. `runPhotoMatchNative` 分块 `classifyOne` -> `classifyItems` 产出 `auto / ambiguous / unmatched`
3. `finishPhotoMatch` 渲染确认 UI，末尾 `maybeCleanInbox()`（有 ambBox 时 return，不删临时文件）
4. 用户点「确认」-> `confirmAmbiguous` / `confirmUnmatched` -> `window.__saveOne = linkOrBase64` -> `Android.linkPhoto(b.id, it.path, name)`

**保存判定（`linkOrBase64`，三端同源）**：
```
if (window.Android && window.Android.linkPhoto) {
  rel = window.Android.linkPhoto(b.id, it.path, name);  // 仅当 it.path 文件存在才返回非空
  if (rel) { push; return true; }
}
if (it.data) { push; return true; }   // 原生管线 it 无 data（为省内存不读 base64）
return false;                          // <- 落到这里 => chosen 不增 => 显示 0
```

**候选根因（按可能性排序，待实跑确认）**：
1. **`it.path` 在确认时已失效**：临时解压目录 `inbox/uz_*` 被提前清理（cleanInbox 时序 / 多次进入 finishPhotoMatch）-> `linkPhoto` 内 `src.exists()==false` -> 返回 "" -> false。尤其 ambiguous 与 unmatched 混存时，处理完 ambiguous 即清理，unmatched 的 path 随后失效。
2. **`it.path` 含中文/空格，经 JSON 回传+`escapeJson` 后路径损坏** -> `File.exists()` 误判为不存在。
3. **非安卓端（Web/Win/UOS）`window.Android` 桥未正确注入或 `linkPhoto` 抛异常** -> catch 返回 ""。

**已确认正常的部分**：
- 安卓 `linkPhoto`（LargeFileManager.java:123）逻辑正确：文件存在则拷贝并返回相对路径，否则返回 ""。
- 安卓 `unzipImages`（:535）GBK/GB18030 探测已修复中文名乱码（前次修复），path 为真实绝对路径。
- Win `linkPhoto`（Program.cs:203）即使 srcPath 不存在也返回非空字符串（**此点有隐患：会假成功计数，但不会导致 0**）。

**修复方向（待确认方案 + 实跑复现后定）**：
- 锁定临时文件生命周期：确认保存完成前**不得**清理 `inbox/uz_*`（改 `maybeCleanInbox` 时机为「所有确认框处理完且保存成功后」）；
- `linkPhoto` 失败时回传具体错误（非空原因）便于定位，而非静默 "";
- 增加「保存后回读校验」：保存后 `readPhoto(rel)` 验证文件确实可访问，失败则计入失败并提示。

## 修复完成（v3.30.2 / v1.6.2 / v1.8.2）

### 问题1：添加建筑物选照片后勾标记丢失

**根因**：input.f 元素右侧的浅蓝大对勾是 **WebView 内置自动填充/已识别状态指示**（安卓 WebView 在识别 input 为姓名/地址类字段时绘制）。`fPhotos.onchange` 里 `openEdit(b)` 整段重建 `editBody.innerHTML`，所有 input.f 元素被销毁，新 input.value 一致但 WebView 还没识别 → 对勾丢失。经纬度因为是数字不触发自动填充，所以截图里"对勾"只出现在"名称/管理所/管理站"。

**修复**：抽 `renderPhotoGrid/buildPhotosHtml/bindPhotoCardEvents` 三个本地函数（在 openEdit 闭包内）。`fPhotos.onchange` 内把 `openEdit(b)` 改为 `renderPhotoGrid()` —— 只刷新 `phGrid` 子树，**保留所有 input.f 元素 DOM**。照片 .rm 删除按钮也改用 `renderPhotoGrid()` 局部刷新。

**修改文件**（共 21 份，三端同源）：
- 水利线 7 份：`android-build/shuili-v329`、`android-build/water-v329`、`native-shell/win-water-webview2/{webroot,publish,publish_win_water,bin/Release/.../win-x64}`、`native-shell/uos-water-pyqt6`、`APK归档/四端安装包_20260824/win-水利-...`
- 感知线 7 份：`android-build/perc-v13`、`native-shell/win-webview2/{webroot,publish_win_perc,bin/Release/.../win-x64,dist}`、`native-shell/uos-pyqt6`、`APK归档/四端安装包_20260824/win-感知-...`
- 古建线 7 份：`travel/webroot`、`travel/android`、`native-shell/win-gujian-webview2/{webroot,publish_win_gujian,bin/Release/.../win-x64}`、`native-shell/uos-gujian-pyqt6`、`APK归档/四端安装包_20260824/win-古建-...`

**验证**：`node --check` 14 份主文件全部 OK；fPhotos.onchange 函数体内 `openEdit(b)` 已被替换为 `renderPhotoGrid()`，6/6 关键文件确认。

### 问题2：zip导入勾选确认保存0张（"修复多次没弄好"的真凶）

**根因**：`finishPhotoMatch` 在把 `ambBox/dupBox/unmbBox` 写入 DOM **之前**调用了 `maybeCleanInbox()`。三个守卫判断（`document.getElementById("ambBox")`等）此时全部为 null → 失效 → 直接执行 `cleanInbox()` → **删掉所有 inbox/uz_* 临时解压目录**。ambBox 渲染后，用户勾选16张点确认 → `confirmAmbiguous` → `linkOrBase64` → `Android.linkPhoto(b.id, a.it.path, ...)` → `a.it.path` 指向的文件**已被删** → `src.exists()` 为 false → 返回 "" → 0 张。

代码注释明明说"此处不立即 cleanInbox"，但函数内却调了——典型的**注释与代码矛盾型 bug**，也是"多次修复没弄好"的原因：之前可能只调过安卓桥的 linkPhoto 路径处理，没发现时序问题。

**修复**：删除 `finishPhotoMatch` 内那个错误调用。清理统一交给 `confirmAmbiguous` / `confirmUnmatched` / `dupOverwrite` 各自末尾的 `maybeCleanInbox()`，它们都在确认 UI 处理完毕后（DOM 已写入）调用，时机正确。

**Node 时序模拟验证**：
- OLD：渲染前就删 `uz_*` → 确认时源文件没了 → 0 张（复现）
- NEW：渲染前不删，确认处理完才删 → 源文件还在 → 能保存（修复）

**修改文件**（共 13 份，水利+感知+Win/UOS 同源）：与问题1相同的活动源副本（古建的 `finishPhotoMatch(pending)` 写法天然正确——blocks 数组守卫代替 DOM 守卫——不存在此 bug）。

**说明**：此 bug 只在**有 ambiguous 待确认项**的导入时出现（auto 匹配本身不依赖 uz_*，会走 `linkOrBase64` 在 finishPhotoMatch 同步阶段就调，`uz_*` 还在）。如果你的 zip 全是 auto 匹配，0 张不会出现；只要有 ambiguous 确认框，**100% 必现 0 张**。

## 关键教训

1. **"对勾"不是代码画的**——是 WebView 内置自动填充标识。修复方案是保留 DOM（`renderPhotoGrid` 局部刷新），而非改 CSS。
2. **"注释说不能做但代码做了"是高危信号**。`finishPhotoMatch` 函数体与上方注释明确矛盾——这种 bug 难发现，因为注释让人误以为已处理。
3. **DOM 守卫 vs 内存守卫**：古建用 `__dupBlocks.length/__ambBlocks.length`（内存）正确，水利用 `document.getElementById("ambBox")`（DOM）但调用时机过早错——**任何"等 DOM 渲染完再清理"逻辑都必须用 setTimeout(0) 或在写入 innerHTML 之后调用**，否则永远踩坑。
4. **静态分析 + 时序模拟是高效定位手段**：本次没真机复现，靠读代码 + Node 模拟时序就定位了时序型 bug。
