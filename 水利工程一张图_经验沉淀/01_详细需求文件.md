# 水利工程基础信息一张图 · 详细需求文件（SRS）

> 版本基线：v3.14（2026-08-16，versionCode=14，author=科技推广中心）
> 用途：对照功能「查漏补缺」——每一项需求都给出**功能点 + 验收标准 + 优先级 + 关键实现函数/文件**，便于逐项勾选核对。
> 适用范围：同类「离线一张图」类 APP（水利设施、视频监控资源、管线、林地……）均可复用本需求框架。

---

## 1. 项目概述

| 项 | 内容 |
|----|------|
| 应用名称 | 水利工程基础信息一张图（APK 显示名「水利工程基础信息图」） |
| 类型 | 安卓离线 APP（WebView 容器，加载本地 `index.html`） |
| 目标用户 | 水利基层管理所/站现场人员、巡查员、工程管理人员 |
| 核心场景 | 野外/现场离线查看水利工程设施点位、属性、照片；采集坐标、导入照片、导出报表 |
| 数据来源 | 奥维互动地图导出的 `.ovkmz`（坐标+工程参数+照片）→ 由 `parse_ovkmz.py` 转 `data.js` |
| 交付形态 | 已签名 APK（可直接 `adb install` 或文件管理器安装，自签名首次需允许未知来源） |

**一句话目标**：把一套网页（地图+数据）离线装进手机，现场无信号也能看图、查属性、拍照片、出报表。

## 2. 技术架构与约束

| 层 | 选型 | 说明 / 约束 |
|----|------|------------|
| 前端框架 | Leaflet.js（本地 `leaflet/`） | 离线必须自带 leaflet.js / leaflet.css，且**不能依赖 leaflet 默认 PNG 图标** |
| 底图 | 天地图 WMTS 在线瓦片 | `vec_w`（矢量）/ `img_w`（影像），token `t{s}`，`subdomains:["0".."7"]`；离线场景需改本地瓦片；**Token 集中在 `index.html` 的 `window.TIANDITU_TOKENS`（browser/server），app.js 读 `browser\|\|内置缺省`，换环境只改一处；server token 不随客户端发布** |
| 标记 | `L.divIcon` 内联 SVG 水滴 | **严禁引用外部图片**，否则离线开天窗 |
| 数据持久化 | `localStorage` | 键名 `shuili_map_v2`；与旧版 `v1` 不冲突 |
| 导出/压缩 | JSZip（本地 `jszip.min.js`） | 照片 ZIP、建筑物 CSV |
| 原生桥 | `Android.*` JSInterface | `openLocationSettings` / `openExternal` / `saveBlob` |
| 打包 | aapt2 + d8 + zipalign + apksigner | 零 Gradle/Studio；见技能 `assets/` |
| 权限 | 定位、存储(≤28)、INTERNET | 见 `AndroidManifest.xml` |

**关键约束（任何改动不得破坏）**
- 所有资源用**相对路径**，`index.html` 内联关键数据（避免 `file://` 下 `fetch` 被拦）。
- 凡是离线地图：标记、图例、装饰一律内联 SVG / CSS，不引用任何外部图片文件。
- 构建必须在**纯 ASCII 路径**下进行（中文路径会让 aapt2/d8 报 bad resource path）。

## 3. 数据模型

建筑物记录（`window.SHUILI_DATA` 数组，每条一个点/线要素）：

| 字段 | 含义 | 必填 |
|------|------|------|
| `id` | 唯一标识（如 `b1`） | 是 |
| `name` | 名称（如「龚庄子进水闸」） | 是 |
| `office` | 管理所（如「西田各庄所」） | 是 |
| `station` | 管理站 | 否 |
| `chan` | 段/渠道（如「西田各庄段」） | 否 |
| `btype` | 建筑物类型（进水闸/交通桥/跌水…） | 是 |
| `lat/lon` | 经纬度（线要素用 `coords` 数组） | 点要素必填；线可取中点 |
| `photos` | 照片列表（批量导入后写入 `{file, caption}`） | 否 |
| `attrs` | 自定义参数 `[["参数名","值"], …]` | 否 |

元数据 `window.SHUILI_META`：`title / author / offices[] / types[] / counts{point,line,nopos,photo,total}`。

## 4. 功能需求（模块清单）

> 每条格式：**功能点 · 验收标准 · 优先级 · 关键函数/文件**。勾选列用于查漏补缺。

### 4.1 地图与底图
- [ ] **矢量/影像底图切换**：右上角悬浮面板单选 + 菜单「底图切换（矢量/影像）」双入口，状态始终同步。
  - 验收：切到影像底图显示卫星图；两个入口任一切换，另一处状态同步。
  - 关键：`buildBaseSwitcher()` / `setBase(mode)` / `switchBaseMap()`（app.js）；`t{s}` token。
- [ ] **底图请求失败不白屏**：瓦片加载失败时地图容器有底色，控制台/UI 给出提示而非整页卡死。
- [ ] **缩放控件位置**：挪到右下角，不与悬浮面板/测距提示重叠。

### 4.2 标记与弹窗
- [ ] **统一蓝色水滴标记**：`L.divIcon` 内联 SVG（蓝 `#1e6fbf`+白点，32×44，描边 2.5px），离线可见。
- [ ] **点要素 vs 线要素**：线要素用折线渲染，弹窗坐标取中点。
- [ ] **弹窗内容**：标题 + 类型 badge + 参数表 + 照片缩略图 + 操作按钮（编辑/导航/删除/关闭）。
- [ ] **关闭按钮**：弹窗「关闭」按钮 + 放大后的 leaflet 关闭按钮（≥28px），防止找不到主界面。

### 4.3 建筑物增删改（CRUD）
- [ ] **添加**：菜单「添加建筑物（点地图定位）」进入添加模式，点地图落点自动取坐标，填表单保存。
- [ ] **编辑**：弹窗「编辑」打开表单，可改名称/管理所/类型/坐标/参数。
- [ ] **删除**：弹窗「删除」带确认。
- [ ] **模式互斥**：坐标拾取/测距/添加「三选一」，进入其一自动退出其它。

### 4.4 筛选
- [ ] **多维筛选**：按管理所/管理站/类型（chip 多选）+ 关键字搜索。
- [ ] **实时生效**：筛选后地图标记与计数立即更新。
  - 关键：`openFilter()` / `passFilter()`（app.js）。

### 4.5 列表视图
- [ ] **卡片列表**：所有建筑物卡片，显示名称/类型/管理所。
- [ ] **快速定位**：列表项「定位」点击立即跳地图并打开弹窗（线要素取中点）。
- [ ] **切换自愈**：从列表切回地图调用 `map.invalidateSize()`，避免地图灰块。
  - 关键：`toggleList()` / `renderList()`（app.js）。

### 4.6 定位
- [ ] **我的位置**：菜单「定位我的位置」唤起 `navigator.geolocation`，显示坐标。
- [ ] **权限拒绝自动跳设置**：PERMISSION_DENIED 时 1.2s 后 `Android.openLocationSettings()`。
- [ ] **超时与类型区分**：TIMEOUT/其他分别提示；超时 10s，`maximumAge:0`。
  - 关键：`locateMe()`（app.js）；`MainActivity` 内 `onGeolocationPermissionsShowPrompt` 自动授权。

### 4.7 导航
- [ ] **唤起第三方地图**：弹窗「导航」构造 `geo:lat,lon?q=lat,lon(中文名)`，`Android.openExternal()` 唤起系统选择器（高德/百度/腾讯）。
- [ ] **中文地名不乱码**：`q` 参数**直接拼中文**，不得 `encodeURIComponent`（会导致 `%E5%B3%B0…` 乱码）。
  - 关键：`appNav()`（app.js）；**CHG-038 教训**。

### 4.8 测距
- [ ] **折线测距**：菜单「测距」进入模式，点地图记点，绘制折线+各段距离+总距离。
- [ ] **结束方式**：双击/按钮结束；模式禁用双击缩放；菜单按钮显示「结束测距」。
  - 关键：`toggleMeasure()` / `clearMeasure()` / `onMeasureClick()` / `fmtDist()`。

### 4.9 周边搜索
- [ ] **半径圈选**：选中心建筑物+半径，画 `L.circle`，按 `distanceTo` 排序结果。
  - 关键：`nearbySearch()` / `appDoNearby()`。

### 4.10 获取坐标
- [ ] **三种取坐标**：GPS 定位 / 点选地图 / 搜索建筑物，结果可一键复制。
  - 关键：`getCoordinates()`。

### 4.11 照片管理
- [ ] **单张上传**：`<input type=file>` 经 `onShowFileChooser` 选图，存到建筑物 `photos`。
- [ ] **批量导入照片（按名匹配）**：
  - [ ] 支持多选图片 **或** 选 ZIP 压缩包，统一收集后匹配。
  - [ ] **忽略末尾数字/括号**：`normalizePhotoName()` 去掉扩展名与末尾数字（「峰山口1.jpg」→「峰山口」）。
  - [ ] **匹配规则**：文件名 base 与建筑物名称相等或相互包含。
  - [ ] **三类结果**：①唯一匹配→自动保存；②0 匹配→计入未匹配并提示；③多匹配→弹勾选框，用户可**多选**保存目标，点「保存勾选的匹配」落库。
  - [ ] **filter 必须 return**：图片/zip 筛选 `filter(fn)` 回调要有 `return`，否则恒为空（**CHG-034 教训**）。
  - 关键：`batchImportPhotos()` / `runPhotoMatch()` / `confirmAmbiguous()` / `normalizePhotoName()`。

## 6. 两日踩坑教训（查漏补缺必读）

| # | 坑 | 现象 | 根因 | 正解 |
|---|----|------|------|------|
| 1 | 字符串未转义引号 | v3.1 启动白屏假死 | 提示串含未转义 `"` 致 `SyntaxError`，整 IIFE 不执行 | `\"` 转义；`node --check` 验证 |
| 2 | 内联 onclick 找不到函数 | `closeSheet is not defined`，弹窗关不掉 | IIFE 局部函数内联处理器访问不到 | `window.openSheet=openSheet; window.closeSheet=closeSheet` |
| 3 | filter 漏写 return | 选单张照片提示「未找到图片文件」 | `files.filter(fn)` 无 return，`imageFiles` 恒空 | 补 `return` |
| 4 | geo: 地名乱码 | 导航显示 `%E5%B3%B0…` | `encodeURIComponent(name)` 被地图 App 当原文 | 直接拼中文，不编码 |
| 5 | 瓦片模板非法 | 整页冻死「Script error.」 | `t{0-7}` Leaflet 不能解析 → `getTileUrl` 抛错 | 用 `t{s}` + `subdomains:["0".."7"]` |
| 6 | 离线图标开天窗 | 标记变「mark」文字 | 依赖 leaflet 默认 PNG 图标，离线无图 | 一律 `L.divIcon` 内联 SVG |
| 7 | 中文路径构建失败 | aapt2/d8 报 bad resource path | 构建路径含中文 | 构建在纯 ASCII 目录，完再拷回 |
| 8 | d8 不吃目录 | d8 报错 | 必须显式传 `.class` | `obj/com/.../MainActivity.class` |
| 9 | aapt2 无 add | 无法注入 dex | 34.0.0 删 `add` | Python `zipfile` ZIP_STORED 注入 |
| 10 | javac 中文注释 | unmappable character | 默认 windows-1252 | `javac -encoding UTF-8` |
| 11 | 沙箱 rm 不可靠 | 残留 apk 致 zipalign 报「Output exists」 | 沙箱禁 `rm -rf` | zipalign 用 `-f -p 4`（`-f` 在前） |
| 12 | 构建目录残留 | 同上 | — | 每次用干净目录或 `-f` 覆盖 |

## v3.10（2026-08-15）导入超大压缩包卡死修复（致命）

> 本次针对用户反馈「导入 2G 压缩包 APP 死机、运行数据 6G、重装不清数据依旧死机、删照片才正常」做根因三连修复。**未删除任何已有功能/菜单**，仅新增「清理导入缓存」菜单项与三个原生桥（`thumbPhoto`/`cleanInbox`/`unzipImages` 改异步）。风格/色彩/字体与 v3.7 起设计系统完全一致，详见 `docs/07_APP风格色彩字体搭配.md`（已随版本升 v3.10）。

### 一、根因剖析（三个独立问题叠加）
1. **主线程同步解压阻塞（表现：导入即死机）**——`unzipImages` 原在 WebView UI 线程**同步**解压数 GB ZIP/7z（LZMA2 极慢），阻塞分钟级，UI 完全冻结。
2. **全分辨率照片 base64 撑爆 WebView 内存（表现：删照片即正常）**——`photoSrc` 经 `readPhoto` 把整张高清图转 base64 塞进 `<img>`，单栋建筑上千张照片一次性渲染 → WebView OOM。
3. **解压临时目录不清理（表现：运行数据飙到 6G、重装仍爆满）**——`unzipImages` 解压到 `inbox/uz_*` 后从不删除，每次导入残留数 GB；重装不清 `getExternalFilesDir` 私有目录，故删除 APP 重装仍死机。

### 二、修复方案
- **异步解压**：`unzipImages(srcPath)` 改 `void`，跑原生线程池 `pool.execute`；流式写盘（7z 不整包入内存）；`progress("unzip",written,srcLen)` 上报进度；完成回调 `window.onUnzipImages('[{name,path}...]')`（失败为 `ERR:` 串）。JS 端 `onPickFiles` 改为异步：先 `openXferProgress("unzip",...)`，逐包调 `window.Android.unzipImages(z.path)`，收齐 `onUnzipImages` 再 `runPhotoMatchNative`。
  - 关键：`LargeFileManager.unzipImages`(java) / `MainActivity` 桥 / `app.js onPickFiles` + `window.onUnzipImages` + `finishUzIfDone`。
- **原生缩略图**：新增 `thumbPhoto(relPath,max)` / `thumbPath(absPath,max)`，用 `BitmapFactory` 先 `inJustDecodeBounds` 算 `inSampleSize`，`RGB_565` 降采样 + JPEG q72 压到边长 ≤ max（默认 720px）返回 base64。`photoSrc` 改返回缩略图；新增 `photoFullSrc(p)` 仅在灯箱/保存时按需单张读全图（`readPhoto`）。
  - 关键：`LargeFileManager.thumbPhoto` / `thumbPath` / `thumbOf`；`app.js photoSrc` / `photoFullSrc`。
- **清理解压临时目录**：新增 `cleanInbox()` 递归删 `inbox/uz_*`；在 `finishPhotoMatch`（导入完成后）、App 启动 `onPageFinished` 后、以及菜单「清理导入缓存（释放空间）」（`cleanImportCache`）三处调用。**只清临时目录，不动已导入照片**。
  - 关键：`LargeFileManager.cleanInbox` / `MainActivity.cleanInbox` / `app.js cleanImportCache` + 启动清理。
- **匹配分块防卡**：`runPhotoMatchNative` 改为每批 30 张 + `setTimeout(0)` 让出主线程，配 `updateXferProgress("match",...)`，避免匹配大批量再次冻结。
- **弹窗照片封顶**：标记弹窗照片列表封顶 `maxShow=18`（含 `loading="lazy"` + 「查看全部 N 张 ›」进灯箱），编辑弹窗封顶 `maxShow=24`，防止一次性渲染上千张。

### 三、智能匹配 / 退出按钮 / 查询筛选（既有要求，本版保留未动）
- 智能匹配 `scoreMatch`（LCS + Levenshtein + 2-gram）在范围内让用户确认卡片更方便（v3.7 起，本版不改）。
- 每页退出按钮 + 三击空白回主菜单（v3.7 起，本版不改）。
- 查询 🔍 / 筛选 🎚️ 最高频按钮置顶显眼；筛选确定 0→toast「没有符合条件的建筑」/1→flyTo/多→倒水滴 + 蓝色虚线圈 + fitBounds（既有，本版不改）。

### 四、验收标准（v3.10）

## v3.11（2026-08-15）导入压缩包后照片未绑定建筑物修复（致命）

> 本次针对用户反馈「导入 2G 压缩包 APP 没死机，但查看建筑物查不到照片、存储数据有 3.9G」做根因修复。**未删除任何已有功能/菜单**，仅强化智能匹配与落盘方式。风格/色彩/字体与 v3.7 起设计系统完全一致，详见 `docs/07_APP风格色彩字体搭配.md`（已随版本升 v3.11）。

### 一、根因剖析（两个独立问题叠加）
1. **匹配只比文件名、范围缩窄不对建筑物名（表现：建筑物查不到照片）**——v3.10 的 `runPhotoMatchNative` / `classifyItems` 只把**照片文件名**（`it.base`）和建筑物名做相似度评分；`matchScopeForFolder` 仅按「管理所 / 类型」缩小候选，**从不对建筑物名**。当用户按 `建筑物A/照片.jpg`（文件夹名即建筑物名、文件名为 `photo001` 这类通用名称）组织压缩包时，`scoreMatch("photo001","建筑物A")=0` → 每张判为「未匹配」→ 全部不绑定 → 建筑物查无照片。
2. **解压文件堆在 inbox 不释放（表现：存储 3.9G 却没照片）**——未匹配照片停在 `inbox/uz_*` 解压临时目录，既没被 `linkPhoto` 落盘，又可能在导入中断/用户中途查存储时裸露为 3.9G，形成「占空间却没照片」的观感。

### 二、修复方案
- **智能匹配双路命中（根因①）**：新增 `bestMatchesForItem(it)`，把照片「所在文件夹的每一层目录名」（如 `管理所X/建筑物A` 拆成 `管理所X`、`建筑物A`）与「文件名」都去和建筑物名评分取最高分；`classifyOne(it)` 据分数分类——`score>=700` 且明显最优（与第二名分差 >200）则**自动绑定**，否则进原有「范围内确认」流程（卡片标置信度、范围标注文件夹路径、全选/全部清除一键）。`建筑物A/照片.jpg` 现正确绑定「建筑物A」。
- **folder 回传完整父路径**：`LargeFileManager.unzipImages` 的 7z/zip 分支把 `jsonItem` 的 `folder` 由「顶层目录名」改为「完整父路径」，支持 `管理所/建筑物/照片.jpg` 多层嵌套命中。
- **linkPhoto 改移动（根因② + 存储优化）**：`linkPhoto` 由 `copyFile` 改为 `renameTo`（移动），跨文件系统失败回退复制。导入来源本就是临时解压目录，`cleanInbox()` 会清剩余，移动安全；2G 解压出 3.9G 直接落盘，**避免再复制 3.9G 造成存储峰值翻倍（约 7.8G）**。导入完成仍自动 `cleanInbox()`。

### 三、智能匹配 / 退出按钮 / 查询筛选（既有要求，本版保留未动）

### 一、问题定位（v3.11 之后的新现象）

1. **导入后建筑物仍查不到照片（统计 13 不变）**——v3.11 的智能匹配对**文件夹里没有建筑物名**的压缩包（如 `管理所A/IMG_001.jpg`，文件夹只到管理所，文件名是相机通用名）所有键 `scoreMatch=0` → 3628 张全部进 `r.unmatched`。而 v3.11 的 `finishPhotoMatch` 对未匹配仅渲染一句「未匹配 3628 张（文件名1、文件名2…）」，**没有任何绑定入口**——用户无路可走，照片虽解压却 0 张入库。这就是「1.7G 空间 ≠ 0 张照片」的根因（同时 `cleanInbox()` 在 `finishPhotoMatch` 末尾会清理未落盘的临时文件，理论上存储会回落；用户观察到的 1.7G 多半含历史 `photos/` 残留）。
2. **统计「13」含义歧义**——`showStats` 只输出「含照片」= 含 ≥1 张照片的建筑物数（13 个），没有「总照片数」。用户把「13」误读为「13 张照片」，导致「导入 3628 张后统计仍 13」像是 bug，其实 0 张入库、统计没变。
3. **缺二级菜单**：批量导入/删除照片、批量删除建筑物都没有二级入口，只能编辑单张删除，不便大量清理。

### 二、修复方案（v3.12）

- **未匹配照片的「批量绑定」确认 UI（根因① 的根治）**：`finishPhotoMatch` 新增 `unmbBox`——共享 `<datalist id="umbBldList">` 列出全部 557 个建筑物（一次构建、轻量复用），未匹配项逐张渲染 `<input list="umbBldList">`（搜/选建筑物）+ 复选框（默认全选）。顶部「一键全部绑定到：[建筑] [+全部应用]」一键预填所有行，「确认」按勾选调用 `linkOrBase64` 落盘。配套 `unmbSelectAll` / `unmbClearAll` / `unmbCancel` / `confirmUnmatched` 一组操作。即使压缩包完全没有建筑物结构（文件名/文件夹都猜不出），用户也能在 5 秒内一键把 3628 张全绑到一个正确建筑物；想精细调整就逐张改 `<input list>`。
- **统计新增「总照片数」并澄清「含照片建筑」标签（根因②）**：`showStats` 增加 `总照片数` 统计卡（`b.photos.length` 累加）+ 把原「含照片」改名为「含照片建筑」，并加一行说明「含照片建筑 = 含 ≥1 张照片的建筑物数；总照片数 = 全部照片合计（含系统内置+导入）」。导入后再看统计，「总照片数」会从原 6 张涨到 3628+6 张，统计口径完全自洽。
- **导入照片加 `added: Date.now()` 时间戳**：为「按时间筛选」提供锚点。`linkOrBase64` 与编辑弹窗内 `b.photos.push` 都写入 `added`，后续「删除添加的照片」按 `days` 窗口过滤。
- **「照片状态」筛选条件（功能 #3）**：`filters.photoStatus` 新增字段 `all | has | many(≥3) | none`；`passFilter` 据此过滤；`openFilter` 渲染「照片状态」互斥单选 chips；`appClearFilter` 重置为 `all`。与既有管理所/管理站/类型筛选组合生效。
- **「删除添加的照片」二级菜单（功能 #1）**：`deleteImportedPhotos()` 弹窗——「时间」chips（全部/近 7/30/90 天）+「管理所」chips + 默认全选的复选清单（按筛选条件动态生成）+ 全选/全部清除/取消/确认 + 二次确认「将删除 N 张（含磁盘文件，不可恢复）」。确认时按 bid 汇总 `pi`（从后往前删避免索引错位），先调 `Android.deletePhoto(rel)` 删磁盘文件再 `b.photos.splice(pi, 1)`，最后 `save();render()`。
- **「删除建筑物」二级菜单（功能 #2）**：`deleteBuildingsMenu()` 弹窗——管理所 + 类型 chips + 含照片数提示 + 复选清单 + ⚠️红字提示「删除后数据不可恢复（建筑物记录及其全部照片将被永久移除）」+ 二次确认「将永久删除 N 个建筑物及其 M 张照片（不可恢复），是否继续？」。确认时先逐张删 `photos/*.jpg`，再 `BUILDINGS.filter(b => !ids.includes(b.id))`，最后 `save();render()`。
- **删除前必弹 confirm 二次确认**：批量删照片与删建筑物都加了二次 confirm 提示，含「不可恢复」明确警示。

### 三、智能匹配 / 退出按钮 / 查询筛选（既有要求，本版保留未动）

## v3.14（2026-08-16）手动匹配照片未真正入库——致命修复
### 一、问题描述
- 用户：导入 368 张压缩包，自动匹配 16 张，其余 352 张手动选择并确认，界面显示 368 张「保存」，但仅自动匹配的 16 张真正与建筑物绑定。APP 未死机。
- 根因①（致命）：`finishPhotoMatch` 匹配后立刻 `cleanInbox()` 删除 `inbox/uz_*` 中未匹配/多选照片源文件；用户手动绑定时 `linkPhoto` 打开已删文件→原生 `!src.exists()` 返回空→静默失败。自动匹配的 16 张因已被 linkPhoto 移出 inbox 而幸免。
- 根因②（假成功）：`confirmUnmatched`/`confirmAmbiguous` 执行 `saveOne(); chosen++;` 无条件 +1，落盘失败也报「已保存」。

### 二、修复方案（v3.14）
- **cleanInbox 延后**：新增 `maybeCleanInbox()`，仅在重复/多选/未匹配三个手动匹配框全部处理完后才清理 inbox；`finishPhotoMatch` 改调它（此时框未处理→跳过）；各 confirm/cancel 处理完各自框后各调一次。
- **真落盘计数**：`confirmUnmatched`/`confirmAmbiguous` 改为 `var ok = saveOne(...); if (ok) chosen++; else skipped++;`。
- **统一重命名**：`linkOrBase64` 用 `seq = b.photos.length + 1`，落盘文件名 `建筑物名_顺序号.jpg`、caption `建筑物名 #顺序号`（自动/手动都适用）。
- **多选框改互斥单选**：`ambBox` 候选改 `<input type="radio" name="amb{i}">`，默认选最匹配项（每张照片只绑一个建筑物）。
- 未删任何功能/菜单；风格色彩字体与 v3.13 一致（见 `docs/07`，已升 v3.14）。
