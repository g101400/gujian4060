# 水利工程一张图 · 开发文档沉淀与记忆体系

一款能长期维护的软件，离不开**文档沉淀**与**记忆体系**。水利一张图把开发过程中产出的资料分门别类管理，本文做个总览——每一类都可单独展开成一篇详文。

---

## 一、工程文档（docs_shuili_v3）

| 文档 | 定位 | 主要内容 |
|---|---|---|
| **01_软件需求说明书（SRS）** | 要做什么 | 运行环境、用户特征、功能需求（地图/标记/筛选/列表/增删改/定位/导航/测距/周边搜索/导入导出/统计/关于/数据管理）、非功能需求、接口（天地图 API、Android 桥）、数据结构 |
| **02_软件概要设计（HLD）** | 怎么做（宏观） | 模块划分、数据流、WebView 承载方式、四端同源策略 |
| **03_软件详细设计（DDD）** | 怎么做（微观） | 关键函数与数据结构、菜单注入、AI 模块适配 |
| **04_软件变更文档** | 改了什么 | 从 v3.0 到 v3.48 每次变更明细（含 CHG 编号、根因、回退说明），是版本脉络的主档案 |
| **05_版本历史与备份** | 何时发的、备份在哪 | 版本时间线 + 回退备份目录索引 |
| **06_四端功能对照表** | 四端差在哪 | 安卓/Win/UOS/iOS 形态、构建链路、功能差异、版本八处同步清单、已知边界 |

> 这六份构成「需求 → 设计 → 变更 → 版本 → 对照」的闭环，任何人接手都能快速看懂全貌。

---

## 二、记忆体系（.workbuddy/memory）

除了工程文档，还有一层**跨会话记忆**，专门沉淀「经验」而非「功能」：

- **MEMORY.md**：长期事实——项目铁律（改 data.js 双门禁、多副本唯一真相源、门禁嵌发版脚本）、关键流程（注入 + 双门禁模式）、坑的防复发条款。
- **问题台账_三图回归_2026-08.md**：每条问题一个编号（T-001…T-044），含现象 / 根因 / 修复 / 验证 / 防复发，是可检索的「错题本」。
- **当日 memo（YYYY-MM-DD.md）**：每天做了什么的一行记录，便于回溯某天改了什么。

记忆与文档的区别：**文档讲功能，记忆讲教训与约定**。文档给人看，记忆给「未来的自己 / Agent」看。

---

## 三、为什么分门别类

- **可复用**：某一类主题（如「UOS deb 构建」）可直接抽出成一篇技术文，不用从零写；
- **可检索**：出问题先查问题台账对应编号，定位快；
- **可继承**：换人或换 Agent，记忆体系让经验不随人走；
- **可审计**：每次发版都能在变更文档 + 版本历史里对账。
